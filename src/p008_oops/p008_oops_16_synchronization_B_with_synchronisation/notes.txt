This is one of the most frequently asked Core Java interview topics.

Before writing any code, let's understand why synchronization exists.

Problem Without Synchronization

Imagine a bank account.

Balance:

₹1000

Two people use the same account.

Thread A → Withdraw ₹500

Thread B → Withdraw ₹500

Both execute at the same time.

Expected Result
₹1000

↓

Thread A withdraws ₹500

↓

₹500

↓

Thread B withdraws ₹500

↓

₹0

Everything is correct.

What Can Actually Happen?

Both threads read the balance at the same time.

Balance = ₹1000

Thread A sees:

1000

Thread B also sees:

1000

Both decide:

"There is enough money."

Then both update the balance.

Now the result becomes incorrect.

This is called a Race Condition.

What is a Race Condition?

A Race Condition occurs when:

Two or more threads access the same data.
At least one thread modifies the data.
The final result depends on which thread executes first.

This leads to unpredictable or incorrect results.

Real-Life Example

Imagine a whiteboard in a classroom.

Student A writes:

Possible result:

The final result depends on who finishes first.

This is a race condition.

Solution: Synchronization

Synchronization tells Java:

"Only one thread can execute this critical section at a time."

Other threads must wait.

Example

Without synchronization:

Thread A
      │
      ▼
Shared Data
      ▲
      │
Thread B

Both can access simultaneously.

With synchronization:

Thread A
      │
      ▼
 LOCK
      │
Shared Data
      ▲
      │
Thread B (WAITING)

Only one thread enters.

The other thread waits.

What is a Critical Section?

A critical section is the part of the program that accesses shared resources.

Example:

balance = balance - amount;

This should never be executed by two threads at the same time.

Java Keyword

Synchronization is done using:

synchronized

Example:

public synchronized void withdraw() {

}

Interview Definition

Synchronization is:

A mechanism that allows only one thread at a time to access a shared resource, preventing race conditions and ensuring data consistency.

This is a common interview question.

Interview Question

Q: If five threads are waiting for a synchronized method, does Java guarantee that the first waiting thread executes next?

Answer:

No. Java does not guarantee FIFO (First-In, First-Out) ordering for acquiring a monitor lock. The JVM scheduler decides which waiting thread gets the lock next.

Golden Rule ⭐⭐⭐⭐⭐

This is worth remembering for interviews.

One Object
      ↓
One Lock
      ↓
One Thread at a Time

If there are:

One Object

→ Only one thread can execute the synchronized method.

If there are:

Two Objects

→ There are two independent locks, so two threads can execute at the same time (one per object).

Real-Life Analogy

Imagine two hotel rooms.

Room 101 🚪

Room 102 🚪

Each room has its own key.

Person A uses Room 101.

Person B uses Room 102.

Can both use their rooms at the same time?

✅ Yes, because each room has its own lock (key).

Now imagine only one room:

Room 101 🚪

Person A is inside.

Person B has to wait outside.

This is exactly how Java synchronization works.
